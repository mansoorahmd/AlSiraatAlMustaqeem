Research Gate Atlas

A map of how MQ Research Gate — a detective's study for the Qur'an — is built, and of the monetization work that just landed. It is also our shared notebook: every section has a feedback thread, and the whole history is kept so we can settle changes here rather than in chat.

How to use this page. Type your name once (top right), then leave notes in the Notes & feedback box under any section. Entries are saved to this page and persist — I read them back and reply in the same threads, marked Claude. The Communication log at the end shows everything in one place.

The one idea to hold onto: studying stays local, offline and free; the community is the paid, cloud layer. Every design choice below follows from that line — and from a hard constraint: you can only charge for what the server holds, never for what already sits on the reader's disk.

01System map

Two worlds share only a login. Everything on the left runs on the reader's own machine and needs no account; the cloud on the right is optional, invite-only, and now the paid surface. The local server is the only thing that touches either local database.

02The two databases

The split is the backbone of everything, including monetization.

📖 quran.db

The reference material — the Book and everything known about its words.

  • Text in four scripts, per-word morphology, roots, ~9 classical lexicons
  • Read-only, ships with the app, ~150 MB
  • Corrections are signed patch releases
  • Moving to Postgres — step 1 done: a copy verified exact, row-for-row (schema corpus)

✒️ research.db

What you build on top — your earned understanding.

  • Cases & board, established meanings, trails, notes, indications, motifs
  • Read + write, self-migrating, the one irreplaceable file
  • Self-describing: a one-row owner table says whose work it is
Why this matters for money. Both files are local. A feature that runs entirely against them can't be enforceably charged for — the code ships on the user's disk. So monetization has to live where the server is in the loop: the cloud.

03Free vs paid — the surface

The dividing line is not a feature list someone picked; it falls out of the architecture. Anything that needs the cloud server is gateable; anything local is not, and should stay free.

Local core free · offline

  • Read the Qur'an — all scripts, morphology, lexicons
  • Open cases, gather evidence, write notes & questions
  • Build & establish your own form meanings, your gloss
  • Study with the AI (MCP), over your own work
  • Back up your research

Community plan · online

  • See the group's established readings & dissent
  • ⚖ Where you stand apart (divergence)
  • Community reading chips in the reader
  • Publish upstream — submit notes, propose claims
  • Moderation & establishment (role-gated, not charged)

Role × plan

Two independent axes: role = what you may do in the research process; plan = what you've paid for. A moderator on the free plan can still moderate.

ActionNeeds roleNeeds active plan
Read the corpus / study locally—no · free
See community readings / divergencereaderyes · pro
Publish (submit / propose claims)researcheryes · pro
Approve / object (review)moderatorno
Establish directly / issue invites / set tiers & policymaintainerno
Read the corpus from the cloud (/corpus/*)—per policy public · signed in · plan ≥ tier
See a locked translation—its tier below it, it's left out

The plan column isn't a fixed pro: tiers are data the maintainer edits — e.g. free (0) ‹ student (50) ‹ pro (100) ‹ scholar (200) — and every gate asks for a minimum tier. pro is the community tier.

04The plan gate

A plan ladder sits beside the role ladder. It is data — the plan_tiers table, each tier a name and a rank — so the maintainer can run free ‹ student ‹ pro ‹ scholar without a deploy. On a paid route, requirePlan(tier) runs after requireRole: role answers “are you allowed to”, plan answers “have you paid for it”. Below the tier the server returns 402 Payment Required, naming the tier needed. It fails closed: an unknown tier never passes, and a lapsed plan counts as free.

The same idea guards the corpus itself: a runtime policy (public, signed_in, or plan ≥ tier, default plan ≥ pro), and an optional tier per translation. Change either with npm run access.

Billing isn't wired yet — a maintainer grants a plan out of band with npm run set-plan -- you@example.org pro 30 or POST /plan. That's the one seam a real payment provider slots into later.

05Community: the change that makes it enforceable

This is the heart of the work. Before, the group's readings were pulled down and mirrored into local derived_* tables so they'd work offline — which also meant they sat on the user's disk, forever, un-gateable. After, they're read live from the remote, gated, and never stored locally.

06Publishing

Offering your work upstream — a note submission or a proposed claim — is a paid action: POST /submissions and POST /claims now carry requirePlan('pro') on top of the role check. In the app, a signed-in publisher without a plan sees a quiet upgrade nudge instead of a button that fails; a plan that lapses mid-action is caught and turns into the same nudge.

Deliberately not gated: a moderator approving or a maintainer establishing. The community's staff run it — charging them to do so would be counter-productive. (One-line change if that ever needs revisiting.)

07The MCP — local, and staying that way (for now)

The MCP lets an AI study the Book with you. When we looked at moving it to the cloud, the blocker was concrete: the cloud had none of the corpus. Every corpus tool — read_ayah, study_root, trace_word, search_quran — reads the local quran.db.

That blocker is now half-lifted: the corpus data is in Postgres and verified (see §08). What's left is the heavy part — porting the query layer from synchronous SQLite to async Postgres — plus the second blocker, which hasn't moved: the AI's proposals only reach you for review if your personal research lives where the AI writes.

Decision (revisit later). Keep the MCP fully local and free — consistent with the app's own free, offline core. Monetization is already complete without it: the enforceable paid surface is the community (reads + publishing), which Phases A–D deliver.
A future “full cloud research” would move personal cases/notes/indications to the cloud so the AI's proposals surface in the app — but that reverses local-first and is a larger migration. Parked, not forgotten.

corpus 1 · done

Corpus → Postgres: move & verify the data

npm run corpus:migrate — 294,804 rows in 18 s, one transaction, verified exact on every row. Text columns COLLATE "C" so Arabic sorts exactly as SQLite does (proven: the هدي forms return in identical order). App & MCP untouched.

access · done

Plan tiers as data + corpus access policy

A runtime tier ladder; reading the corpus is public, signed_in or plan ≥ tier; translations can require their own tier (hidden below it). Proven end to end through the real app.

corpus 2 · in progress

Corpus → Postgres: port the readers

Content done — chapters, verses, words, neighbours, translations at /corpus/*; corpus:parity compared 7,152 answers with SQLite, all identical. Next: search (an Arabic tokenising decision), roots & lexicons, linkages, echoes, similarity, spellings, wazn.
